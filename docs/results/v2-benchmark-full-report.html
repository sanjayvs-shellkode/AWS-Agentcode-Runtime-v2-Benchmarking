Key Finding: At 50 concurrent requests, V2 maintains consistent ~1.8s overhead while V1 overhead explodes to 25+ seconds. V2's snapshot-based architecture handles concurrency much better because each session restores from a pre-made snapshot rather than starting from scratch.

What We Implemented

1. Warmup Endpoint (/warmup)

async def warmup_handler(request): warmup_type = request.headers.get( "X-Amzn-Bedrock-AgentCore-Runtime-Warmup-Type" ).lower() if warmup_type == "memory": # Pre-load boto3 client (survives in snapshot) _bedrock_client = boto3.client("bedrock-runtime") # Import heavy modules from strands import Agent from strands.models import BedrockModel elif warmup_type == "disk": # Prime SSL certificates and HTTP paths http_requests.get("https://example.com", timeout=5) # Register the warmup route app.add_route("/warmup", warmup_handler, methods=["POST"])

2. CDK/CloudFormation Configuration

hooks_configuration = RuntimeHooksConfigurationProperty( build_property=BuildLifecycleHooksProperty( warmup=LifecycleHookProperty( action=LifecycleHookActionProperty( http_post=HttpPostLifecycleHookActionProperty( path="/warmup", port=8080 ) ) ) ) )

3. V2 Snapshot Safety Constraints

Conclusions

Finding Details
V2 is the big win Switching from V1 to V2 reduces cold start overhead by 66-71% (4.9s → 1.4s)
Warmup adds modest benefit The /warmup hook saves ~200ms (13%) on cold starts
V2 excels at concurrency At 50 concurrent requests, V2 maintains 1.8s overhead vs V1's 25s
Warm requests are equal Both V1 and V2 perform the same on subsequent requests in a session
Basic warmup is sufficient Simple HTTPS requests in disk phase work as well as complex MCP calls
Recommendation: Use V2 with the /warmup endpoint for production workloads. The snapshot-based architecture provides consistent low-latency cold starts, especially important for applications with bursty traffic or many concurrent users.
