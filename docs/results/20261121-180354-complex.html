AgentCore Runtime V1 vs V2: Strands Weather Agent

The same Strands agent (Claude Haiku 4.5, three tools behind AgentCore Gateway and Lambda: geocode_city, get_forecast and convert_temperature; conversation history in AgentCore Memory) is deployed twice, once on platform version V1 and once on V2, with the same code package and settings. Each runtime answered ten multi-city questions that need all three tools as cold starts, as warm calls on one session, and in concurrent bursts of 1, 10, 50 new sessions. 162 measured calls, region ap-south-1, started 2026-11-21 12:33:54 UTC.

Method and limits

  • Runtimes: V1 = wxbench_weather_v1 (version 4, platform V1); V2 = wxbench_weather_v2 (version 4, platform V2).
  • Request path: client → AgentCore Runtime → Strands agent → Bedrock (application inference profile, Claude Haiku 4.5) and AgentCore Gateway → Lambda → Open-Meteo.
  • Session IDs are new UUIDs per cold call and per burst call. Warm calls reuse one UUID per runtime; its first (setup) call is excluded.
  • Server time is the agent's POST /invocations span from AgentCore Observability. Overhead = client latency − server time, which covers session startup and network between this client and ap-south-1. Calls without a matched span: 0.
  • Bursts send all calls at once from one client. AgentCore's quota in this account is 25 new sessions per second, so the x50 bursts can be throttled; throttled calls are listed as failures, not retried.
  • Bedrock throttling inside the agent is retried by Strands, so it shows up as longer server time, not as a failure.
  • The agent keeps conversation history in AgentCore Memory per session, so warm calls carry the earlier turns of their session and send more tokens as the session grows.
  • Small samples: 10 calls per sequential scenario. P50 is a usable comparison; P75, P95 and Max are rough.
